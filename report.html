GCR Under-Reporting in merch_precheck_gdexp_14156_AAB_99

F2P anti-join in the order metrics data cube is globally scoped, incorrectly excluding conversions that appear as direct orders in other experiments.

Verdict: 86 of 115 Starter f2p conversions ($9,957 of $13,329) are dropped for treatment1. The f2p anti-join checks paid orders against ALL experiments instead of scoping per-experiment. This is a platform bug in order_metrics.sql, not specific to this experiment.

Root cause: f2p anti-join over-scoped in cube path

The f2p CACHE TABLE in order_metrics.sql uses an anti-join to prevent double-counting: if a paid conversion order already exists as a direct order in experiment_order_cache, exclude it from f2p.

The anti-join (lines 181–194)

LEFT JOIN (    SELECT order_id, row_id    FROM experiment_order_cache    GROUP BY order_id, row_id) eeoON fe.paid_bill_id = eeo.order_idAND fe.paid_bill_line_num = eeo.row_idWHERE ...
AND eeo.order_id IS NULL   -- exclude if paid order exists as direct order
AND eeo.row_id IS NULL

hivemind-business-analytics/queries/experiment_kpis/order_metrics.sql:181-194

Why it breaks in the cube path

In the Level 4 SQL path (normal execution), experiment_order_cache is filtered by scorecard_template_name. The anti-join only checks orders within the same scorecard. Narrow scope → correct behavior.

In the cube path (MetricCubeJob), strip_scorecard_filters() removes the scorecard filter. experiment_order_cache now contains all orders from all experiments across all scorecards. The anti-join checks paid orders against this global set — a conversion order that’s a direct order in any experiment gets excluded from f2p for every experiment.

Why this disproportionately affects treatment

  • Treatment creates Starter trials (subline=Starter). Their f2p conversions are real paid product orders that commonly appear in experiment_order for other experiments → anti-joined out → visible GCR loss.
  • Control creates Free trials (subline=Free). Their f2p conversions are also anti-joined out, but the stats engine filter already excludes product_pnl_subline_name = 'Free' → the loss is invisible.

4. sqlglot rewrite verified locally

Tested rewrite_full_sql() on the f2p CACHE TABLE statement using the production extra_columns list. sqlglot parses CACHE TABLE as a Cache node in Spark dialect. The f2p SQL passes through without corruption — the anti-join subquery’s GROUP BY is unchanged. The bug is not in the rewrite; it’s in the anti-join’s implicit assumption that experiment_order_cache is scoped to one scorecard.

Proposed fix

Add experiment_id and cohort_id scoping to the f2p anti-join subquery. In the Level 4 SQL path this is a no-op (already scoped by scorecard). In the cube path it correctly scopes the anti-join per experiment.

Before — order_metrics.sql:181–194
LEFT JOIN (
    SELECT order_id, row_id
    FROM experiment_order_cache
    GROUP BY order_id, row_id
) eeo
ON fe.paid_bill_id = eeo.order_id
AND fe.paid_bill_line_num = eeo.row_id
After
LEFT JOIN (
    SELECT order_id, row_id, experiment_id, cohort_id
    FROM experiment_order_cache
    GROUP BY order_id, row_id, experiment_id, cohort_id
) eeo
ON fe.paid_bill_id = eeo.order_id
AND fe.paid_bill_line_num = eeo.row_id
AND eo.experiment_id = eeo.experiment_id
AND eo.cohort_id = eeo.cohort_id

hivemind-business-analytics/queries/experiment_kpis/order_metrics.sql

The same fix applies to post_rollout_order_metrics_workflow.py which uses the same SQL template for post-rollout cubes.

Scope of impact

This is a platform-level bug affecting every experiment that relies on f2p conversions through the order metrics data cube. An experiment is affected when:

  • Users sign up for free/trial products that later convert to paid
  • Those paid conversion orders also exist as direct orders in other experiments (extremely common — a single order appeared in 39 experiments)
  • The metric’s named filter includes the trial’s PNL subline (so the loss is visible in the scorecard)

Severity scales with user overlap across experiments. On GoDaddy’s platform, a typical user is bucketed into 30–40 experiments simultaneously, so most paid conversion orders will exist in experiment_order for many experiments.
